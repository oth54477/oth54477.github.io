v1.20.3upstream 릴리스 반영

빌드는 성공하는데 배포하면 죽는 결함, upstream에서 고쳤다

CI가 원리적으로 못 잡는 조용한 실패 — 이슈 등록부터 릴리스 반영까지 하루.

문제
eager: true shared 사용 시 프로덕션 빌드 산출물이 부팅 시점에 크래시. 빌드는 EXIT 0·경고 0으로 정상 종료 — 배포 후 런타임에만 드러난다.
접근
5개 버전 영향 매트릭스로 결함 도입 버전을 실측 정정(1.16.1 → 1.17.0). 재현 필요조건 3가지를 분리해 파일 6개 최소 재현으로 축소. 원인이 번들러가 아니라 플러그인의 정규식 후처리임을 산출물 수준에서 특정 — 네임스페이스 import가 "함수 호출이 없다"는 이유로 삭제되고 있었다.
결과
첫 수정안이 기존 테스트를 깨뜨리자 판정 기준 자체를 "호출되는가"에서 "참조되는가"로 교체. PR 머지 → v1.20.3 릴리스, upstream 테스트 1,017개 통과. "빌드 성공"과 "산출물이 동작함"은 다른 명제다.
자세히 — 결함의 구조와 규명 과정

결함의 구조 (단순화한 요지)

// 플러그인 후처리: Vite preload 헬퍼를 지우려는 정규식이 모듈 경로를 보지 않고
  // `{ _ as X }` 형태의 import를 전부 매칭한 뒤, X의 "함수 호출"이 없으면 문장째 삭제한다.
  // 네임스페이스 import는 값으로만 참조되므로 여기 걸려 지워졌다.
  if (!hasCall(local, chunk)) dropImportStatement()          // 판정: 호출되는가

  // 수정(v1.20.3): 판정 기준을 "참조되는가"로 교체 — 기존 동작 보존, 결함만 제거
  if (!new RegExp(`\\b${local}\\b`).test(chunk)) dropImportStatement()

과정

  • 사내 빌드에서 증상 발견 — 기존 보고 이슈 0건인 미보고 결함. 사내 코드 주석의 "1.16.1부터"가 실측으로는 1.17.0부터임도 함께 정정
  • 초기 합성 재현이 실패한 원인을 청크 토폴로지 차이로 좁혀, 재현 필요조건 3가지(eager shared · 다중 entry · 앱 소스의 런타임 직접 import)를 분리
  • 빌드 중 정규식 콜백에 로그를 심어 삭제되는 문장을 직접 포착 — 어느 후처리 단계인지까지 특정
  • 메인테이너가 1.5시간 만에 머지한 별도 수정이 호출부만 제거한 것임을 지적하고 근본 수정 PR로 연결
  • 회귀 테스트가 fix 없이는 실패함을 확인하고, 배포 tarball에 수정 판정식이 실제로 들어갔는지까지 검증

Architecture · Vite ↔ Webpack
수십 곳고객사 프로덕션 무장애 가동

이종 번들러 Module Federation — 돌아가던 MFA에 Vite를 붙이고, 운영 데이터로 다시 설계했다

"Vite를 쓰려면 전체를 마이그레이션해야 한다"는 팀 내 전제를 POC 하나로 반박했다.

문제
기존 솔루션은 Webpack + Vue 3이고, 팀은 합류 전인 2023년부터 Webpack 내장 Module Federation으로 Remote를 운영하고 있었다. 신규 Host는 React + Vite로 만들려 했는데 "Vite를 쓰려면 전체를 Vite로 마이그레이션해야 한다"는 전제가 붙어 기술 전환 자체가 막혀 있었다.
접근
그 전제를 검증부터 했다 — @module-federation/vite로 Vite(Host) ↔ Webpack(Remote) 런타임 통신이 성립함을 POC로 먼저 입증하고 Host 측 Vite MF 도입을 주도했다. React Query와 Vue Query가 단일 Query Client를 공유하도록 통합해 두 프레임워크가 같은 API 캐시를 참조한다. 이후 타 팀 소유 Remote의 빌드 설정을 webpack 내장 ModuleFederationPlugin에서 @module-federation/enhanced(MF 2.0)로 전환하고 런타임을 0.21.6 → 2.8.1로 올렸으며, remote 로딩을 remoteEntry.js 직접 참조에서 mf-manifest.json 기반으로 이관했다 — manifest의 publicPath가 루트로 내려오는 환경은 런타임 플러그인으로 방어하고 remoteEntry 경로는 폴백으로 남겼다.
결과
2025년 3월 릴리스 이후 수십 개 고객사 프로덕션에서 장애 없이 가동 중. 전체 재작성 없이 신규는 Vite, 기존은 Webpack을 유지하는 점진적 경로를 확보한 것이 핵심 결과이고, 이 경로로 이후 Remote 2종이 각 팀 손으로 Vite에 이전했다. 개발 서버 HMR이 10초대에서 1초 미만으로 바뀐 것은 그 덕에 따라온 이득이다. 이어 6개월 운영 데이터로 런타임 유연성의 비용(파드 4개 상주·월 2~3건 통합 장애)을 정량화해 통합 빌드 아키텍처 전환을 설계했다 — 자신이 붙인 구조를 데이터로 부정하는 것도 같은 사이클의 일부다.
자세히 — 구조도와 운영 중 잡은 결함

운영 중 잡은 결함

  • shared 버전 오보 — Host가 실제 번들한 것과 다른 버전을 공유 스코프에 광고해, singleton 승자 선정이 왜곡될 수 있던 상태를 빌드 산출물 manifest와 설치 트리 실측 대조로 규명·수정. 재발 방지 가드를 빌드에 내장하고 일부러 깨뜨려 실제로 차단됨을 역방향 검증
  • 로컬은 통과·CI만 실패하는 빌드 — 플러그인의 의존 버전 조회가 패키지 매니저 hoist 승자(설치 형태에 따라 달라지는 비결정 값)로 풀린다는 점을 규명. 컨테이너 없이 hoist 디렉터리만 조작해 CI 실패를 로컬에서 결정적으로 재현하고, 실제 번들되는 사본에서 읽은 버전을 주입해 비결정성 의존 자체를 제거
  • 메모리 누수 — React와 Vue의 생명주기 차이로 발생한 구독 누수를 cleanup 로직 분리(unmount 시 리스너 정리·구독 해제)로 해결

파드 4 → 1배포 단위 통합

통합 빌드 아키텍처 — 파드 4개를 1개로 합치고, 런타임 통합은 남겼다

마이크로 프론트엔드는 배포 빈도가 높은 조직에서 값을 낸다. 저빈도 온프레미스 모델에서는 아니었다.

문제
런타임 통합만으로 운영한 첫 6개월간 K8s 파드 4개 상주, 공통 컴포넌트 4중 중복, 월 2~3건 런타임 통합 장애가 남았다. 고객사 데이터센터에 직접 설치되는 제품이라 상주 파드 하나가 그대로 설치·운영 비용이다.
판단
운영 모니터링 데이터로 그 비용을 정량화해 판정 기준을 배포 빈도로 세웠다 — 독립 배포를 실제로 자주 하는 조직이라야 런타임 통합이 값을 낸다. 분기 단위로 릴리스하는 온프레미스 모델에서는 통합 빌드가 우수하다는 결론에 도달했고, 사내 표준으로 문서화했다.
조치
모노레포를 도입해 Remote 3종 + Host를 한 번에 빌드하고 산출물 전부를 단일 nginx 이미지에 적재했다. 바뀐 것은 배포 단위뿐이고 모듈 통합은 여전히 런타임 Module Federation이다 — 각 팀의 저장소와 독립 개발 흐름은 그대로 뒀다.
결과
앱별 독립 파드 4 → 단일 이미지·파드 1. 2026년 6~7월에 구현해 고객사 환경에 배포·운영 중이고, 같은 모노레포를 기반으로 솔루션 공통 디자인 시스템을 개발하고 있다. 아키텍처는 조직의 배포 빈도에 종속된다 — 유행이 아니라 그게 판정 기준이다.

CI 636초 → 158초 — 채택한 조치만큼 철회한 조치가 산출물

잡을 빠르게 만드는 것과 파이프라인을 빠르게 만드는 것은 다른 문제였다.

규명
정적분석 350초 중 269초가 분석이 아니라 파일 트리 순회 — pnpm 심볼릭 링크가 실파일 7.5만 개를 33만 경로로 부풀리고 있었다. CPU를 두 배로 늘려도 총시간이 그대로인 원인을 스케줄링(큐잉 76초 + 스테이지 직렬화 82초)으로 특정해 사장시간 82초 → 3초.
규율
직접 넣은 조치 1건을 실측으로 철회하고, 다른 1건은 산술이 반대임을 확인해 착수 전에 기각. 절감폭 −68%짜리 안은 "이후 모든 테스트가 실행 순서를 의식해야 하는 영구 부채"라는 이유로 의도적 보류. 대조군 표준편차가 목표 효과를 압도하자 "측정 불가"를 계산으로 판정하고 중단. 좋은 수치가 항상 채택 근거는 아니다.
결과
파이프라인 636초 → 158초(4.0배), 정적분석 잡 350초 → 80초(4.4배).

재발 방지 게이트를 known-violations로 고른 이유

  • 숫자 상한은 통과한다. 하나 고치고 하나 새로 만들면 총계가 같아 게이트가 열린다
  • 경로 정규식 예외는 과잉 면제된다. 의도한 순환 하나를 빼주려던 예외가 그 파일이 낀 다른 순환까지 통째로 면제한다. 그래서 순환 경로 자체를 기억하는 known-violations 방식을 골랐다
  • 게이트도 검증 대상이다. 새 순환을 실제로 잡는지 프로브를 심어 확인했다 — 예외로 등록된 파일이 낀 새 순환도 잡힌다. 기존 lint 잡에 한 줄로 붙여 파이프라인 비용 증가를 15초로 묶었다(별도 잡은 install·캐시로 35~40초를 더 낸다)

번들 산출물 실측으로 리팩터를 착수 전에 기각했다

  • host 앱의 barrel(index.ts) 233개 전면 정리 요구에 대해, tsconfig paths를 해석하는 정적 분석 스크립트로 barrel 경유 import 735건을 계량화하고 636건(387파일)을 자동 치환하는 코드모드를 작성해 A/B 빌드를 3회씩 반복 측정
  • 결과는 반대였다 — 번들 크기가 오히려 0.07% 증가하고 청크가 169 → 172개로 파편화. Rollup이 ESM 재수출을 이미 tree-shake하므로 barrel 자체는 번들 비용이 아니고, 제거 시 청크 파편화가 Module Federation 환경에서 오히려 손해다

E2E 식별자 자동 부여 — 가장 자신 있던 결론을 스스로 반증했다

이미 발행한 문서를 정정하고 주입 축을 컴파일 타임으로 재설계. 남길 만한 것은 결과가 아니라 검증 과정이다.

반증
"호스트 1회 배선으로 타 팀 공수 70~85 인일 소거"라는 자기 결론을 적대적 검증으로 기각 — 런타임 정보로는 데이터 건수·권한·정렬에 흔들리지 않는 식별자를 만들 수 없다 (실측: 라우트당 동종 컴포넌트 26개 이상).
설계
Vue 컴파일러 nodeTransform으로 빌드 타임 주입. 템플릿 AST에서 업무 의미를 추출하는 9단계 폴백 + 위치 기반 스냅샷 병합으로 문구 수정이 테스트를 깨뜨리지 않게. 해결 안 되는 구간은 "해결했다" 대신 미보증 등급으로 정직하게 표기.
상태
Host 앱 범위로 설계·구현해 MR을 머지했으나 되돌렸고, 현재 운영에는 반영돼 있지 않다. 검증 빌드 측정치는 보증 등급 요소 자동 라벨 도달률 83.2%·식별자 충돌 0건이지만 프로덕션 성과로 주장하지 않는다. 남은 것은 과정이다 — 플러그인 테스트가 프로덕션과 다른 컴파일 옵션으로 돌던 사각지대를 발견하고 빌드 산출물 스냅샷 대조 검증을 추가해 숨은 결함 3건을 잡았다.

왜 addon-vitest를 배제했나

  • 권장 경로인 @storybook/addon-vitest는 browser mode와 Playwright를 요구한다 — 게이트 1개를 위해 브라우저 런타임을 CI에 들이는 비용은 이 규모에서 과하다고 판단해 대체 경로를 택했다
  • 같은 목적은 portable stories로 jsdom에서 달성했고, 브라우저 기반 E2E 실행 레이어는 별도 축으로 분리했다 — 판정의 전제가 규모이므로 규모가 달라지면 다시 평가한다
